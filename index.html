쿠버네티스 이관과 GitOps 운영 체계

VM crontab에서 NKS + Argo CD로

VM에서 crontab으로 돌던 배치와 상주 봇을 네이버 클라우드 쿠버네티스(NKS)로 옮기고, Argo CD 기반 GitOps 배포 체계 위에서 운영한 실무 프로젝트. 컨테이너 이미지 빌드부터 배포, 시크릿 관리, 장애 대응까지 단독 수행했습니다.

2026.08 ~ 2026.09단독 수행
OVERVIEW

회사에는 이미 NKS와 Argo CD 기반 배포 인프라가 있었지만, 제가 만든 파이프라인만 그 밖에서 VM crontab으로 돌고 있었습니다. 서버에 SSH로 들어가 스크립트를 고치는 방식이라 배포 이력이 남지 않았고, 장비에 종속돼 복구도 어려웠습니다. 기존 GitOps 체계 안으로 편입시켰습니다.

세 워크로드를 옮겼습니다. 커뮤니티 게시 배치는 CronJob, 상시 대기하는 Slack 봇은 Deployment, 창업 지원 서비스 Mallo는 웹 Deployment와 뉴스레터 CronJob으로 구성했습니다.

컨테이너화가 가장 까다로웠습니다. 파이프라인이 Python과 Node.js CLI, Playwright Chromium을 모두 요구해 단일 이미지에 담아야 했습니다. Playwright 공식 베이스 이미지를 골라 시스템 라이브러리 의존성을 베이스에서 해결했고, requirements.txt를 앱 코드보다 먼저 COPY해 코드가 바뀌어도 설치 레이어를 재사용하도록 했습니다. 개발은 Apple Silicon, 운영은 amd64라 buildx로 크로스 빌드했습니다.

트러블슈팅 / 의사결정 1

배포 체계 설계 — 클러스터에 붙지 못하는 상태에서 배포하기

문제

GitOps는 모든 것을 Git에 선언해야 하는데, DB 접속 정보와 토큰은 평문으로 올릴 수 없었습니다. 쿠버네티스 기본 Secret은 base64 인코딩일 뿐이라 그대로 커밋하면 유출입니다.

게다가 제 로컬 kubectl은 회사 클러스터에 접근이 막혀 있어(401), 클러스터에 붙어서 봉인할 수도 없었습니다. VM 스크립트가 손으로 처리하던 중복 실행 방지와 로그 회전, 재시작 루프도 옮길 방법이 필요했습니다.

조치
  1. SealedSecret을 도입해 클러스터 공개키로 암호화한 봉인본만 커밋했습니다. 공개키만 따로 받아 오프라인으로 봉인했고, 평문이 디스크에 남지 않도록 파이프라인으로 연결했습니다.
  2. VM 스캐폴딩을 쿠버네티스 기본 기능으로 치환했습니다.
  3. 워크로드 성격에 따라 리소스를 나눴습니다. 배치는 실행 후 종료되므로 CronJob이고 Service가 필요 없으며, 연결을 유지하는 봇은 Deployment입니다.
  4. 실제 클러스터에 올리기 전, 로컬 kind 클러스터에 Argo CD와 SealedSecret 컨트롤러를 띄워 전 과정을 리허설했습니다.

매니페스트만 보고도 무엇이 언제 어떻게 도는지 알 수 있는 구조가 됐고, 배포는 PR 머지로 끝납니다. 시크릿은 봉인본만 저장소에 남습니다.

배운 점

배포를 명령이 아니라 선언으로 바꾸면 추적과 자가 치유가 따라옵니다. 리소스를 고르는 일은 복사가 아니라 워크로드 성격을 판단하는 일이었습니다.

트러블슈팅 / 의사결정 2

표준에서 벗어난 결정과 무중단 컷오버

문제

회사 배치 표준은 재시도 3회였는데, 이 워크로드는 한 번 실행에 LLM 호출 비용이 큽니다. 3회 재시도는 실패 시 비용이 세 배가 된다는 뜻이었습니다.

스케줄도 문제였습니다. CronJob의 schedule은 기본 UTC이고, timeZone 필드는 쿠버네티스 1.27 이상에서만 동작해 클러스터 버전에 의존하게 됩니다.

컷오버는 더 위험했습니다. 이 배치는 결과를 실제로 기록하기 때문에, VM과 쿠버네티스가 동시에 돌면 같은 내용이 두 번 올라갑니다.

조치
  1. 재시도 횟수를 낮췄습니다. 게시 작업은 재시도하면 중복 게시 위험이 있고 LLM 호출 비용도 큽니다. 한 사이클 실패는 다음 사이클이 흡수하므로, 표준을 따르지 않은 이유를 매니페스트 주석에 남겼습니다.
  2. timeZone 필드 대신 UTC로 환산해 적었습니다. 한국은 서머타임이 없어 UTC+9로 연중 고정이므로 환산이 안전하고, 클러스터 버전에 의존하지 않습니다. 가독성은 주석으로 보완했습니다.
  3. 회차별로 CronJob을 따로 두지 않고 하나로 합쳤습니다. concurrencyPolicy는 같은 CronJob 안에서만 겹침을 막기 때문에, 나눠 두면 아침 작업이 늦게 끝났을 때 점심 작업이 겹쳐 뜹니다.
  4. 컷오버는 단계로 나눴습니다. CronJob을 suspend 상태로 먼저 올리고, 일회성 검증 Job으로 실제 시각대 실행을 확인한 뒤, 검증 Job을 지우고 VM crontab을 먼저 제거한 다음 CronJob을 켰습니다. 짧은 공백을 감수하고 이중 기록을 원천 차단했습니다.
결과

이중 발행 없이 전환을 마쳤고, 재시도 정책과 스케줄 표기는 근거를 남긴 채 표준과 다르게 유지됩니다.

배운 점

팀 표준은 지키는 것이 기본이지만, 워크로드 특성상 다르게 해야 한다면 근거를 남기고 설득하는 편이 낫습니다. 운영 중인 작업을 옮기는 일은 만드는 일과 다릅니다. 순서를 정하는 것이 절반이었습니다.

트러블슈팅 / 의사결정 3

운영 중 장애와 관측의 한계

문제

클러스터를 kubectl로 직접 조작할 수 없어, 관측과 조작을 전부 Argo CD와 Git으로만 해야 했습니다. 그런데 Argo CD가 Healthy로 보인다고 실제로 일이 잘 된 것은 아니었습니다. 파드가 종료 코드 0으로 끝나면 내부에서 실패했어도 Healthy로 표시되고, 완료된 파드의 로그는 사라져 원인을 볼 수도 없었습니다.

운영 중 세 가지 장애를 겪었습니다. 외부로 나가는 경로가 몇 주 뒤 끊겼고, 터널 파드가 CrashLoopBackOff에 빠졌으며, 뉴스 생성과 게시가 동시에 멈췄습니다.

조치
  1. 첫 번째는 터널 노드키 만료였습니다. 화면에는 연결됨으로 보였지만 실제로는 끊겨 있어, 직접 핑으로 확인한 뒤 재인증하고 서버 노드의 키 만료를 끄는 쪽으로 정리했습니다.
  2. 두 번째는 터널 인증키 만료였습니다. 공개키로 SealedSecret을 재봉인해 교체했습니다.
  3. 세 번째는 노드 메모리 압박이었습니다. 파드가 축출되면서 두 작업이 함께 죽었습니다. 고메모리 타입 노드풀을 증설하는 것으로 정리됐고, 저는 실측을 근거로 파드의 메모리 요청량을 조정했습니다. 게시 1회분의 실질 피크가 약 1.9GB이고 그중 브라우저가 1.84GB였는데, 요청량은 실사용보다 낮게 잡아 노드 용량을 선점하지 않도록 했습니다.
  4. 관측 갭은 코드로 메웠습니다. 실패 시 사유와 화면을 오브젝트 스토리지에 덤프하도록 보강해, 파드가 사라져도 증거가 남게 했습니다.
결과

세 장애 모두 복구했고, 실패 원인을 사후에 확인할 수 있는 경로를 만들었습니다.

점검 과정에서 상태 저장이 전체 성공 조건에 묶여 있어, 일부 채널만 실패해도 큐와 이력이 기록되지 않는다는 것을 뒤늦게 발견했습니다. 결과 알림과 상태 저장을 분리하는 쪽으로 고치고 있습니다.
배운 점

보이는 상태와 실제 상태는 다를 수 있습니다. 연결됨으로 표시되는 화면보다 직접 확인한 응답이 정확했습니다. 도구가 주는 Healthy는 리소스가 정상이라는 뜻이지 일이 잘 됐다는 뜻이 아닙니다. 관측이 부족하면 남는 기록을 스스로 만들어야 합니다.

  • 전수 재검사에서 시기가 맞지 않는 기사 네 건을 잡아냈습니다
  • 운영 DB는 읽기 전용으로만 접근해 서비스 데이터를 보호했습니다
  • Slack으로 이슈를 생성하고 기존 이슈에 붙은 기사를 확인할 수 있습니다

트러블슈팅 / 의사결정

서비스 데이터를 지키면서 무인으로 돌리기

문제
  • 운영 DB에 파이프라인이 쓰기까지 하게 두면, 배치 실수 한 번에 서비스 데이터가 손상될 수 있었습니다
  • 매 사이클마다 이슈 전체를 다시 돌리면 데이터가 늘수록 시간과 연산 비용이 같이 커집니다
  • 모델이 만든 문장을 그대로 적재하면 원문에 없는 내용이 독자에게 나갈 수 있었습니다
조치
  1. 운영 DB는 읽기 전용 계정으로만 접근하고, 계정 권한과 별개로 코드에서도 쓰기 질의를 막았습니다
  2. 결과물은 분리된 PostgreSQL 22개 테이블에만 적재하도록 나눴습니다
  3. 전체 재처리를 버리고, 새 데이터가 붙은 이슈만 갱신하는 증분 처리로 전환했습니다
  4. 적재 앞에 검증 단계를 두어 원문에 없는 문장과 기간을 벗어난 날짜를 걸러냈습니다
결과

작업량이 전체 규모가 아니라 그날 들어온 데이터 양에만 비례하게 됐습니다. 전수 재검사에서 시기가 맞지 않는 기사 네 건을 잡아냈고, 현재 62개 이슈가 하루 두 번 갱신됩니다.

배운 점

장애를 기다렸다가 고치는 것보다, 처음부터 실수해도 서비스 DB는 살리는 경계를 만드는 일이 중요했습니다. 모델 출력을 믿지 않고 코드가 검증하는 지점을 정해 두면 무인 운영에서도 결과를 신뢰할 수 있었습니다.

PROJECT.3

커뮤니티 자동화 파이프라인

반복 작업의 자동화와 클라우드 이관

커뮤니티 채널에 콘텐츠를 올리던 반복 작업을 배치 파이프라인으로 자동화하고, 로컬 장비 과부하와 IP 차단 문제를 겪으면서 실행 환경을 네이버 클라우드로 옮긴 경험입니다.

OVERVIEW

뉴스보이 기사를 커뮤니티에 올려 서비스 유입을 만드는 일을 기획하고 자동화했습니다. 수집과 분석, 리라이트, 게시로 작동하는 배치 파이프라인으로 운영했으며 아침과 점심, 저녁에 실행되도록 했습니다. Slack Webhook과 연동해 실행 결과와 장애를 상시 확인합니다.

성과

  • 커뮤니티 채널 4개를 상시 운영했습니다
  • 건당 처리 시간은 약 10분입니다
  • 어디에서나 같은 명령으로 동일하게 동작하도록 기술화했습니다
  • 운영 기간 제재 이슈는 0건이었습니다
  • SEO 개선과 병행한 뒤 구글 서치 콘솔 기준 일일 방문자가 158명에서 1,759명까지 올랐습니다

이 파이프라인은 이후 쿠버네티스로 이관했습니다. 자세한 내용은 프로젝트 1에 있습니다.

트러블슈팅 / 의사결정

코드가 아니라 자원과 네트워크가 원인이었던 두 번의 장애

문제
  • 사무실 장비에서 LLM 호출이 한 번에 2.5GB 가까이 점유해, 같은 장비의 다른 배치들이 간헐적으로 멈췄습니다
  • 클라우드로 옮긴 뒤에는 데이터센터 대역이 차단되어 게시가 전부 실패했습니다
조치
  1. 실패하는 작업이 매번 달라 처음에는 각 작업의 코드를 의심했습니다. 실행 시각을 대조해 보니 중단 구간이 전부 자동화가 도는 시간대와 겹쳤고, 연산을 네이버 클라우드로 분리했습니다.
  2. 연산은 클라우드에 두고, 외부로 나가는 브라우저 트래픽만 SSH 터널로 사무실 회선을 거치게 경로를 나눴습니다.
  3. 브라우저 제어용 로컬 포트까지 프록시를 타 응답이 느려져, 그 포트를 프록시 예외로 두었습니다.
결과

세 번째 시도에서 두 문제가 동시에 풀렸고, 파이프라인을 다시 가동했습니다.

배운 점

오류 원인이 코드가 아니라 자원과 네트워크일 수 있다는 점입니다. 그리고 알림이 없으면 장애를 늦게 압니다. Slack으로 실행 결과를 밀어 보내, 찾아가지 않아도 실패가 보이게 만들었습니다.

PROJECT.4

Mallo

창업 지원 AI 서비스

말로 설명하면 사업계획서가 만들어지는 서비스. 음성 전사부터 문서 생성과 내려받기, 뉴스레터 정기 발송 배치와 결제까지 전 구간을 개발했습니다.

운영 중인 서비스 보기
OVERVIEW

창업자가 말한 내용으로 사업계획서를 만들어 주는 서비스입니다. 사업계획서 생성과 맞춤 뉴스레터, 홍보 콘텐츠 자동 제작 세 상품을 운영합니다.

음성 전사부터 문서 생성과 내려받기, 구독 결제와 환불 웹훅까지 서비스 전 구간을 맡았습니다. 뉴스레터는 쿠버네티스 CronJob이 정해진 시각에 호출하고, 사내 뉴스 검색 서비스를 MCP로 연동해 근거를 확보합니다.

성과

  • 사업계획서와 뉴스레터, 홍보 콘텐츠 세 상품을 결제까지 붙여 상용화 단계에 올렸습니다
  • 근거를 정부 공고와 뉴스, 보도자료, 공시에서 모아 붙입니다
  • 한글과 워드, PDF 내려받기를 붙여 사업계획서를 바로 제출할 수 있게 만들었습니다
  • 이슈 파이프라인에서 쓰던 정기 실행 구조를 그대로 옮겨 세 번째 구축이 가장 빨랐습니다
  • 아직 실사용자가 없어 발송은 본인 계정으로 검증하는 단계입니다

트러블슈팅 / 의사결정

정기 발송에서 중복과 부분 실패 다루기

문제
  • 사람마다 하루 한 통이라는 제약이 있어, 크론이 겹쳐 돌거나 파드가 둘이면 같은 사람에게 두 번 발송될 수 있었습니다
  • 한 통을 만드는 데 모델 왕복이 두 번 필요해, 한 요청에 여러 명을 몰면 로드밸런서가 먼저 끊었습니다
  • 지원사업 공고와 정책은 기사가 아니라 공고문이라 뉴스 검색으로는 찾을 수 없었습니다
조치
  1. 보내기 전에 발송 자리를 먼저 확보해 중복 발송을 막았습니다
  2. 한 번에 소수만 처리하고 나머지는 다음 주기가 가져가도록 나눴습니다
  3. 한 사람이 실패해도 기록만 남기고 나머지 발송은 그대로 진행되도록 격리했습니다
  4. 토픽별로 출처를 갈라, 기사로 찾을 수 있는 것만 사내 서비스로 보내고 나머지는 검색에 남겼습니다
  5. 결제 웹훅에 서명 헤더가 없어 주소에 비밀값을 두어 호출을 제한했고, 처리에 실패하면 성공 응답 대신 오류 코드를 돌려주어 재발송이 가능하게 했습니다
결과

연동이 끊겨도 검색으로 대체해 뉴스레터가 멈추지 않게 했고, 출처는 모델이 아니라 코드가 붙이도록 했습니다.

배운 점

중복 방지와 배치 크기 조절, 부분 실패 격리는 워크플로 도구가 다루는 문제와 같은 성격이었습니다. 완벽한 출처보다 발송이 멈추지 않는 쪽을 택하는 것도 설계 판단이라는 것을 배웠습니다.

PROJECT.5  /  학습 프로젝트

AWS 3-Tier 망분리 인프라

AWS 실습 with Terraform

AWS SAA로 배운 VPC와 서브넷, ALB, Auto Scaling, RDS 개념을 Terraform으로 직접 구성한 학습 프로젝트입니다. 이틀간 진행했습니다.

OVERVIEW

10.0.0.0/16 VPC를 Public과 App, DB 3계층으로 나누고 서울 리전 두 가용 영역에 서브넷을 배치했습니다. App과 DB는 private 서브넷에 두어 외부 직접 접근을 막고, App의 아웃바운드만 NAT Gateway로 열었습니다.

자격증으로만 익힌 구성을 검증 가능한 인프라로 옮겨 본 것이 목적이었습니다. 수동으로 서버를 올리면 같은 환경을 반복해서 만들고 지우기 어려워, 전부 코드로 정의했습니다.

검증한 것

  • 로드밸런싱: ALB 접속 시 두 가용 영역의 서버가 교대로 응답
  • 자가 치유: App을 강제 종료한 뒤 Auto Scaling이 인스턴스를 다시 생성
  • DB 격리: 외부에서 RDS 접속 시 타임아웃

실제 트래픽 부하 테스트와 과금, 스케일 정책까지는 가지 못했습니다. 다음에는 CPU 기반 스케일 정책과 GitHub Actions의 terraform plan부터 붙이려 합니다.
